# Анализ существующих механизмов Cua Driver (Prior Art)

В соответствии с п. 3.1 ТЗ проведено исследование встроенных механизмов безопасности и аудита в Cua Driver 0.34.0.

### 1. Авторизация и ограничение полномочий (Agent Authorization)
* **Режимы доступа (`--permission-mode`):**
  * `standard` (по умолчанию) — обычный режим автоматизации без интерактивных подтверждений.
  * `bounded` — требует указания статического манифеста возможностей (`--capability-manifest <path>`) и явного подтверждения запуска (`--approve-capability-manifest`).
  * `unrestricted` — запуск с полным обходом ограничений (`--dangerously-bypass-approvals`).
* **Ограничения встроенного манифеста Cua Driver:**
  * Манифест является статическим и задается только при старте демона (`serve`), не поддерживая динамическое обновление на лету.
  * Манифест ограничивает набор доступных инструментов MCP и профили браузеров Chromium, но **не предоставляет динамического фильтра приложений по Bundle ID** macOS (отсутствует проверка `allowedApps` / `deniedApps` в реальном времени по `pid` / `window_id`).
  * Отсутствует механизм экстренной остановки (Kill-switch) через файловый триггер без перезапуска процесса.

### 2. Аудит и логирование действий
* **Встроенный аудит Cua Driver:**
  * Экспериментальный модуль `--experimental-history` (`cua-driver history`) записывает локальную зашифрованную историю сессий, ориентированную на отладку траекторий.
  * Отсутствует структурированный текстовый лог в формате JSONL с маскированием чувствительных данных (`logTypedText: false`) для внешней SIEM/аудит-системы.
  * Cua Driver собирает анонимную телеметрию (`telemetry`), но она не содержит данных о действиях агента или содержимом экрана.

### Заключение
Встроенных возможностей Cua Driver недостаточно для выполнения требований безопасности (динамический Bundle ID allowlist/denylist, лимиты сессии, маскирование ввода, мгновенный kill-switch). Необходим собственный слой политик и аудита в прокси-сервере (`agent-computer-use`), реализуемый в рамках Фазы 2.
